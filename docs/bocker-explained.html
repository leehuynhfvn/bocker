Giải Phẫu Bocker

Toàn bộ bocker chỉ hơn 100 dòng Bash — không daemon, không binary riêng. Nó chạy được vì Linux kernel đã có sẵn mọi thứ cần thiết; bocker chỉ là lớp gọi lệnh mỏng phía trên.

01 — Nền tảng

Năm nguyên hàm kernel

Bocker không tự phát minh cơ chế cô lập nào. Mỗi "tính năng Docker" trong nó là một lời gọi trực tiếp tới một cơ chế đã nằm sẵn trong kernel Linux từ lâu. Đây là bảng tra cứu dùng xuyên suốt phần còn lại của trang.

Nguyên hàm kernelLệnh trong bockerVai trò
btrfs subvolume btrfs subvolume create / snapshot Filesystem copy-on-write, phân lớp → chính là "image layer"
network namespace ip netns · veth · bridge0 Cho container một stack mạng riêng, nối vào host qua cáp ảo
namespaces khác unshare -fmuip Cô lập mount table, hostname, IPC, cây PID
chroot chroot $btrfs_path/$uuid Đổi thư mục gốc "/" mà process nhìn thấy
cgroup v2 cpu.weight · memory.max Giới hạn CPU và RAM cho toàn bộ cây process
02 — Lưu trữ

Image, container và commit chỉ là một thao tác

Không có "định dạng image" đặc biệt. Một image bocker là một btrfs subvolume chứa nguyên một cây thư mục rootfs. bocker run tạo container bằng cách snapshot subvolume đó — copy-on-write, gần như tức thì, chỉ ghi phần khác biệt xuống đĩa. bocker commit làm ngược lại: snapshot container đang có thành một image mới.

03 — Tham chiếu hàm

Từng hàm trong bocker

bocker_check() nội bộ

"Cơ sở dữ liệu" của bocker không phải một file JSON hay SQLite nào cả — nó chính là kết quả của btrfs subvolume list. Hàm này chỉ hỏi kernel: id này có tồn tại trên đĩa không.

btrfs subvolume list "$btrfs_path" | grep -qw "$1" → 0 nếu có, 1 nếu không
bocker_init() image
bocker init <directory>

Biến một thư mục local thành image: sinh id ngẫu nhiên img_42xxx, tạo subvolume mới bằng btrfs subvolume create, rồi cp --reflink=auto nội dung vào — reflink nghĩa là copy-on-write, gần như không tốn thêm dung lượng đĩa. Đây là "build" thô sơ nhất có thể tưởng tượng.

bocker_pull() image
bocker pull <name> <tag>

Nói chuyện thẳng với Docker Registry HTTP API v2 — không cần Docker daemon nào cả:

  1. Xin token ẩn danh từ auth.docker.io.
  2. Lấy manifest (JSON mô tả image); nếu là manifest-list đa kiến trúc, chọn nhánh linux/amd64.
  3. Đọc danh sách layer digest — mỗi layer là một blob .tar.gz.
  4. Tải từng layer, giải nén chồng lên nhau vào cùng một thư mục.
  5. Gọi lại bocker_init để biến thư mục đó thành image.
Kéo image thật ra chỉ là: tải vài file tar, giải nén đè lên nhau. "Layer" không hơn gì một bản diff nén.
bocker_rm() · bocker_images() · bocker_ps() sổ sách

rm xoá image lẫn container theo cùng một cách — btrfs subvolume delete — vì cả hai vốn là cùng một loại đối tượng. images và ps chỉ ls các subvolume theo tiền tố (img_* / ps_*) rồi cat một file metadata cạnh nó. Không có daemon giữ trạng thái trong bộ nhớ — filesystem chính là trạng thái.

bocker_run() trái tim
bocker run <image_id> <command>

Đây là hàm dài nhất và cũng là câu trả lời thật sự cho "container là gì". Bốn nhóm việc, theo đúng thứ tự trong code:

  1. Mạng — tạo cặp veth (như một sợi cáp ảo hai đầu): một đầu cắm vào bridge0 của host, đầu kia đẩy vào network namespace mới của container; gán IP 10.0.0.X/24.
  2. Filesystem — btrfs subvolume snapshot từ image sang container (xem sơ đồ ở mục 02); ghi resolv.conf và file lệnh.
  3. Giới hạn tài nguyên — tạo thư mục cgroup, ghi cpu.weight / memory.max, rồi nhét PID hiện tại vào cgroup.procs.
  4. Cô lập & thực thi — vào network namespace, unshare -fmuip để tạo namespace mount/uts/ipc/pid mới, chroot đổi gốc filesystem, rồi mới chạy lệnh của bạn.
bocker_exec() runtime
bocker exec <container_id> <command>

Ngược lại với unshare. Bocker dò qua ps -eo pid,args để tìm PID của tiến trình unshare -fmuip đang đại diện container, lấy PID con thật sự của nó, rồi dùng nsenter -t <pid> -muinp chroot ... để "nhảy vào" đúng các namespace đã tồn tại thay vì tạo namespace mới.

bocker_logs() runtime

cat một file .log mà bocker_run đã ghi bằng tee khi container chạy. docker logs thật cũng không khác về nguyên lý — chỉ là daemon hứng stdout/stderr thay vì shell.

bocker_commit() image
bocker commit <container_id> <image_id>

Xoá image đích, rồi btrfs subvolume snapshot từ container thành image mới cùng tên (xem sơ đồ mục 02). Một trạng thái container tạm thời trở thành image tái sử dụng được — chỉ bằng một phép snapshot.

bocker_help() & dispatcher CLI

bocker_help trích các comment #HELP ngay trong chính file script bằng sed — tài liệu tự sinh từ code, không có file riêng để lệch pha. Ở cuối file, một khối case $1 in ... map trực tiếp bocker <verb> sang hàm bocker_<verb> — toàn bộ "CLI framework" chỉ có vậy.

04 — Rút ra

Học được gì để hiểu Docker

  • 01

    Image là một cây thư mục, không phải định dạng bí ẩn

    rootfs + một chút metadata. Docker thêm layer riêng biệt (overlay2) và checksum, nhưng bản chất không đổi.

  • 02

    Layer là tarball

    Pull = tải vài file .tar.gz theo digest rồi giải nén chồng lên nhau. Registry chỉ là REST API trước một kho blob.

  • 03

    Container không phải máy ảo

    Nó là một process của host, chỉ bị bọc bởi namespaces (tầm nhìn), cgroups (tài nguyên) và chroot/pivot_root (gốc filesystem) — như sơ đồ mục 03.

  • 04

    Copy-on-write là lý do container khởi động nhanh

    docker run không copy image — nó snapshot. Bocker dùng btrfs; Docker thật thường dùng overlay2, cùng một ý tưởng.

  • 05

    Mạng container = veth pair + bridge + NAT

    docker0 của Docker chính là bridge0 ở đây — không có gì thêm về nguyên lý.

  • 06

    Daemon không phải phần lõi

    Nó cộng thêm: API, quản lý vòng đời, build cache, phân phối image, giám sát an ninh — nhưng phần "chạy container" thì đúng như bocker_run.

Những gì bocker cố tình bỏ qua

  • User namespace / rootless — bocker bắt buộc chạy root, không có -U trong lệnh unshare.
  • seccomp, AppArmor, Linux capabilities — không giảm quyền syscall nào cho container.
  • Overlayfs nhiều lớp thật sự — bocker làm phẳng mọi layer khi giải nén, không giữ chúng tách biệt.
  • pivot_root thay vì chroot — chroot vẫn có thể thoát ra được trong một số điều kiện; production runtime dùng pivot_root.
  • Healthcheck, restart policy, volume driver, image signing.
